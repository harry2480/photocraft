# 自動操作のセキュリティ

自動操作は権限境界である。リクエストによって、ファイルシステムへのアクセス、アプリケーションの制御、UI 入力、環境設定の変更、レンダリング、コマンド実行が引き起こされうるからである。

## 現在の実装

- デスクトップのコントロールは `127.0.0.1` にバインドし、1 行につき 1 つの JSON リクエスト/応答を使う。
- ヘッドレス TCP は、ループバック以外のアドレスへのバインドに成功した場合、それを拒否する。
- デスクトップコントロールとヘッドレス TCP のすべての接続は、メソッドのディスパッチ前に 256 ビットのベアラートークンで認証しなければならない。
- エンコードされたリクエスト行は 1 MiB、アクティブな TCP 接続は 16、ヘッドレス/MCP のバッチは 256 ステップに制限される。
- JSON-lines の応答とエンコードされた MCP ツールの結果は 8 MiB に制限される。保持されるバッチ応答には
  合計の予算があり、使い切ると以降のステップを停止する。ヘッドレスの stdio JSON-lines トランスポートは
  TCP と同じリクエスト/応答の上限を適用する。
- ヘッドレスのプレビューは、合成の前に、要求された辺が 2048 ピクセルを超えるもの、およびソースドキュメントが
  67,108,864 ピクセルを超えるものを拒否する。フルサイズの要求も辺の上限に収まる必要がある。レンダリング
  された PNG は、base64 エンコードやファイル書き込みの前に 5 MiB に制限される。信頼されたローカルの CLI
  レンダリングは従来の動作を維持する。
- MCP ブリッジは受信する応答のサイズを制限し、過大な応答の後に操作を再試行しない。スクリーンショットの
  デコードには、寸法、ピクセル数、アロケーションについて個別の上限がある。
- MCP は通常 stdio を使い、オプションでループバックのコントロール TCP にブリッジできる。
- ブリッジと UI のリクエスト経路はタイムアウトを使う。
- エンジンのコマンドは、パニックせずに不正なパラメーターを拒否することが求められる。
- リモートのファイルシステムメソッドは、個別に付与される読み取り用と書き込み用のディレクトリケイパビリティを使う。
- 自動操作のパスは、該当するルート配下の相対パスでなければならない。絶対パス、親ディレクトリへの
  トラバーサル、代替の区切り文字、Windows のデバイス名、不正な形式のコンポーネント、リンクによる脱出は、
  ファイルへの作用が起きる前に拒否される。
- いまだにアンビエントなパスを使うエンジンコマンドは、自動操作の境界でフェイルクローズする。合成された
  UI 入力も同じコマンドポリシーを通り、自動操作によって起動されるファイルフックは、ユーザーが設定した
  スクリプトイベントのパスを実行しない。

## 既知の制限事項

- クライアント単位やツール単位のケイパビリティがない。
- ファイルシステムの読み取り/書き込み権限を超えた、クライアント単位やツール単位の汎用的なケイパビリティモデルがない。
- JSON の深さに関する明示的なポリシー、ドキュメント/セッションのメモリの合計の計上、コンポジターの
  スクラッチ領域の計上、コマンドの実行時間/キャンセルの予算がない。
- 受け付けた TCP 接続ごとに 1 スレッドを使う。
- 構造化されたセキュリティ監査イベントのストリームがない。
- デスクトップのスクリーンショットの取得/エンコード、およびドキュメントの読み込み/書き出しには、自動操作
  固有の処理予算がない。デスクトップのトランスポートは、応答が生成された後にその応答を制限する。
- 高コストなエンジンコマンドがセッションの予算に計上されない。

応答の拒否は、コマンドが状態を変更した後に起こることがある。そのようなエラーは、操作が完了している可能性が
あることを報告する。バッチの応答予算を使い切ると、通常のコマンドエラーであればバッチの続行が許される場合でも、
以降のステップは停止する。それ以前の編集はロールバックされない。正式なプロトコルリファレンスは
[コントロールプロトコル](../automation/制御プロトコル.md)を参照のこと。

## 提案中のセッションモデル

トランスポートは現在、メソッドの探索より前に、暗号学的に安全な乱数で生成された認証情報から認証済みの接続を確立する。将来のセキュリティゲートウェイは、この認証済み接続を、短命でケイパビリティによってスコープが限定されたセッションへと変換すべきである。

残りのケイパビリティは明示的かつ組み合わせ可能であるべきである。例:

```text
DocumentRead
DocumentWrite
UiInspect
UiControl
FilesystemRead (implemented as a root capability)
FilesystemWrite (implemented as a separate root capability)
PreferencesWrite
ApplicationControl
```

名前と粒度は設計上の提案にとどまる。重要な性質は、ドキュメントの閲覧を許可されたクライアントが、任意のファイル書き込み、ポインター入力の注入、環境設定の変更、アプリケーションの終了を暗黙的に許可されないことである。

## 提案中のリクエスト予算

ゲートウェイは、次の項目について有限の値を適用し、テストすべきである。

- リクエストのバイト数と JSON のネスト
- バッチのステップ数と、ネスト/再帰的な呼び出し
- 同時接続数と、クライアントごとの処理中リクエスト数
- レンダリングの寸法と、返すペイロードのバイト数
- ドキュメントのピクセル数、デコード後のバイト数、セッションのメモリの合計
- エンジンが対応している場合は、コマンドの実行時間またはキャンセル

制限は安定したエラーで失敗し、高コストな処理の前に適用され、安全なグローバル上限の範囲内でのみ設定可能であるべきである。監査イベントには、セッションの識別子、ケイパビリティの判定、メソッド/コマンド ID、結果、所要時間、伏せ字化されたパスハンドルを記録すべきであり、ファイルの内容、トークン、シークレットは記録すべきではない。

## 現時点での運用ガイダンス

stdio を優先し、コントロール TCP は必要なときにだけ起動し、読み取りと書き込みのルートは最も狭く付与し、
非公開のトークンファイルを使い、リスナーはループバックに置き、最小権限の OS アカウントを使い、信頼できない
エージェントを機微なファイルから隔離すること。ベアラートークンをコミットしたりログに出力したりしないこと。
暗号化されていないループバックのプロトコルを、トンネルやプロキシで別のホストに中継しないこと。
