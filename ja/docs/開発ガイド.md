# 開発ガイド

## 前提条件

- Rust stable（1.90 以上）。Web ターゲットは `rustup target add wasm32-unknown-unknown` で追加します。
- macOS、Windows、Linux のいずれか。Linux では `libxkbcommon-dev libwayland-dev libx11-dev libxrandr-dev libxi-dev libgl1-mesa-dev libgtk-3-dev` が必要です。

## ビルドと実行

```sh
cargo run --release -p photocraft -- path/to/image.psd      # desktop app
cargo run --release -p photocraft -- --control 7878 --control-token-file .private/control.token \
  --automation-read-root work --automation-write-root work
cargo test --workspace                                     # everything
cargo xtask ci                                             # fmt + clippy + tests + layers + wasm
cargo xtask stats                                          # tests and lines per crate
cargo xtask parity                                         # Photoshop menu coverage -> docs/parity.md
```

画像処理コードは `opt-level 0` では遅いため、ワークスペースのプロファイルでは依存クレートを `opt-level 2` でビルドしています。対話的に操作する場合は必ず `--release` を使ってください。

## 環境変数

| 変数 | 効果 |
|---|---|
| `PHOTOCRAFT_CONTROL_PORT` | `--control <port>` と同じ |
| `PHOTOCRAFT_CONTROL_TOKEN` | 制御用 TCP の 64 桁 16 進ベアラートークン（環境変数を覗かれうる共有システムでは使用を避ける） |
| `PHOTOCRAFT_CONTROL_TOKEN_FILE` | 制御用ベアラートークンファイルを読み込む（サーバー側では作成する） |
| `PHOTOCRAFT_AUTOMATION_READ_ROOT` | 自動化による読み込みを許可するディレクトリ（ケイパビリティ）。リクエストは相対パスを使う |
| `PHOTOCRAFT_AUTOMATION_WRITE_ROOT` | 自動化による書き込みを許可する別のディレクトリ（ケイパビリティ）。リクエストは相対パスを使う |
| `PHOTOCRAFT_CPU_CANVAS=1` | wgpu シェーダーキャンバスの代わりに CPU キャンバスパスを強制する |
| `PHOTOCRAFT_GPU_TILE=2048` | GPU キャンバスのタイル分割を強制する（タイル境界のテスト用） |
| `PHOTOCRAFT_FX_NOCACHE=1` | CPU のレイヤー効果マップキャッシュ（`compose::effect_maps`）を経由しない |
| `PHOTOCRAFT_CPU_COMPOSE=1` | wgpu キャンバスは維持しつつ合成を CPU で行う（snapshot example などで GPU と CPU の描画結果を比較する用途） |
| `PHOTOCRAFT_FX_TRACE=1` | 再構築ごとに、GPU 効果用のシェイプと距離場の計算に費やした CPU 時間を出力する |
| `PHOTOCRAFT_THEME_FILE=tokens.json` | **デバッグビルドのみ:** デザイントークンをライブで上書きする。変更時に再読み込みされる |

### ライブデザイントークン

```json
{ "card": "#323232", "tab_strip": "#262626", "accent": "#378ef0", "radius": 4 }
```

キーは `theme::Tokens`（`crates/ui-egui/src/theme.rs`）のフィールド名です。アプリの実行中にファイルを編集・保存すると、再コンパイルなしで即座に変更が反映されます。この機能はリリースビルドではコンパイル時に除外されます。

## アプリをプログラムから操作する

非公開のトークンファイルを指定してアプリを起動すると、`127.0.0.1:7878` で認証付きの JSON Lines を受け付けます。

```sh
TOKEN=$(tr -d '\r\n' < .private/control.token)
printf '%s\n' "{\"id\":\"auth\",\"method\":\"auth\",\"params\":{\"token\":\"$TOKEN\"}}" \
              '{"id":1,"method":"engine.execute","params":{"command":"layer.newAdjustmentLayer.hueSaturation","params":{"hue":30}}}' \
              '{"id":2,"method":"ui.screenshot","params":{"path":"evidence/shot.png"}}' | nc 127.0.0.1 7878
```

すべてのメソッドは `docs/control-protocol.md` を参照してください。ヒント:

- **macOS は隠れたウィンドウを描画しません。** `ui.screenshot` は最初にウィンドウを前面に出します（デフォルトで `focus: true`）。その他の目視確認の前には `ui.focus` を使ってください。
- **キャプチャは自分のウィンドウだけに限定してください。** ネイティブのキャプチャ（実際のタイトルバーや信号機ボタンを確認したい場合）はウィンドウ ID で取得し（`screencapture -l <CGWindowID>`）、他のアプリが写り込みうる画面領域指定は使わないでください。
- **ポインタージェスチャー:** `ui.pointer` は*ドキュメント*座標でイベントを受け取り、マウスと同じツールのステートマシンに流します。

## ヘッドレス CLI

`apps/photocraft-cli` はバイナリ `photocraft-cli` をビルドします。

```sh
cargo run -p photocraft-cli -- convert in.psd out.pcraft               # any supported format -> any
cargo run -p photocraft-cli -- info out.pcraft                          # JSON: size, mode, depth, layer tree
cargo run -p photocraft-cli -- run in.png --cmd layer.new.layer --params '{"name":"Ink"}' \
                                          --cmd filter.blur.gaussian --params '{"radius":3}' --out out.psd
cargo run -p photocraft-cli -- run --new '{"width":800,"height":600}' --cmd document.inspect
cargo run -p photocraft-cli -- batch --actions actions.json --in photos/ --out done/ --format jpg
cargo run -p photocraft-cli -- commands --filter blur                    # the command registry
```

`actions.json` は `[{"command": "<id>", "params": {…}}, …]` という形式で、記録されたアクションと同じ形です。`run` はコマンドの結果ごとに 1 行の JSON を出力します。

## ネイティブフォーマット（.pcraft）

`crates/format` はロスレスなネイティブバンドルを定義します。STORE エントリの ZIP か、同じレイアウトのディレクトリのいずれかです。

- `manifest.json`: バージョン付きのドキュメントツリー。マイグレーションは `format/src/migrate.rs` にあります。
- `tiles/<blake3>.zst` と `blobs/<blake3>.zst`: zstd で圧縮されたオブジェクト。非圧縮バイト列の BLAKE3 ハッシュでコンテンツアドレス指定されます。
- `thumb.png` と `composite/preview.png`: プレビュー。

開いているドキュメントごとに `PcraftWriter` を 1 つ保持してください。そうすると再保存時には変更のあったタイルだけを圧縮・書き込みし、ディレクトリ形式のバンドルでは参照されなくなったオブジェクトをガベージコレクトします。`format::Autosaver` はバックグラウンドスレッドでリカバリ用ディレクトリにスナップショットを書き込みます。`list_recovery` / `recover` / `discard_recovery` がクラッシュリカバリを実装しています。

`photocraft-io` は `import`/`export` で `.pcraft` をこのクレートに振り分けます。判定はマジックナンバーまたは拡張子で行います。

## MCP（エージェント）

`photocraft-cli mcp` は `rmcp` 上に構築された `crates/automation` を使い、stdio で MCP を提供します。

- **ヘッドレス:** `photocraft-cli mcp --automation-read-root <dir> --automation-write-root <dir>`。プロセス内のエンジンセッションを操作します。ルートを省略した場合、ファイルへのアクセス権はありません。
- **実行中のアプリ:** `photocraft --control 7878 --control-token-file <private-path> --automation-read-root <dir> --automation-write-root <dir>` を起動し、次に `photocraft-cli mcp --bridge 127.0.0.1:7878 --control-token-file <private-path>` を実行します。ルートはデスクトッププロセス側が保持します。`docs/control-protocol.md#mcp-bridge` を参照してください。

ツール:

- `session_list`
- `doc_open`、`doc_new`、`doc_save`、`doc_export`、`doc_inspect`、`doc_render_preview`（PNG 画像を返す）、`doc_select`、`doc_close`
- `command_list`、`command_run`、`command_batch`（1 回の呼び出しで複数コマンド）
- ブリッジ専用: `ui_inspect`、`ui_screenshot`、`ui_pointer`、`ui_menu_invoke`、`ui_set`、`control_call`

Claude Code（リポジトリルートの `.mcp.json`、または `claude mcp add`）:

```json
{
  "mcpServers": {
    "photocraft": {
      "command": "/path/to/photocraft/target/release/photocraft-cli",
      "args": ["mcp"]
    },
    "photocraft-live": {
      "command": "/path/to/photocraft/target/release/photocraft-cli",
      "args": ["mcp", "--bridge", "127.0.0.1:7878", "--control-token-file", "/private/path/photocraft-control.token"]
    }
  }
}
```

```sh
cargo build --release -p photocraft-cli
claude mcp add photocraft -- "$PWD/target/release/photocraft-cli" mcp
```

`doc_inspect`（およびエンジンコマンド `document.inspect`）は、レイヤーツリーを種類、
バウンディング、マスク、選択範囲、効果（`effects.items[].kind`）、スマートフィルター（`smartFilters[]`）、テキストの
内容、調整の設定値、チャンネル、ヒストリーとともに返すので、エージェントはスクリーンショットなしで
自分の操作結果を検証できます。リファレンスは `crates/automation/tests/agent_tasks.rs` で、MCP のみで
操作する現実的な 10 個の編集タスク（タイトルカード、カラーグレーディング、取り消し/やり直し、編集可能なスマートぼかし、
マスク、選択範囲の保存、整列、ケイパビリティで範囲を限定したエクスポート、リサイズ/切り抜き、CMYK + ネイティブ保存）を含みます。

MCP を使わない場合、`photocraft-cli serve [--port N]` がヘッドレスセッションを開いたまま JSON Lines に応答します
（`docs/control-protocol.md#headless-server` を参照）。

典型的なエージェントのループ:

1. `doc_open {path}`
2. `command_list {filter:"blur"}`
3. `command_run {id:"filter.blur.gaussian", params:{radius:4}}`
4. `doc_render_preview` で結果を確認
5. `doc_save {path:"out.pcraft"}`

## カラーマネジメント

`crates/cms` は純 Rust による独自の ICC エンジンです（v2/v4 のパース、matrix/TRC および LUT プロファイル、
4 つすべてのレンダリングインテント、黒点補正）。Adobe の CMYK プロファイルはプロプライエタリなため、合成で作った
"Photocraft Coated CMYK" を含む CC0 の組み込みプロファイルを同梱しています（`crates/cms/README.md` を参照）。

- ドキュメントは埋め込み ICC プロファイル（`Document::icc_profile`）を任意で持ちます。`edit.assignProfile`
  と `edit.convertToProfile` でこれを変更します。モード変更（`image.mode.*`）は cms を通して変換します。
- **校正表示**（⌘Y）、**校正設定**、**色域外警告**（⇧⌘Y）は 3D LUT
  （`cms::Lut3d`）を生成し、それをキャンバスのシェーダーが適用します。ドキュメントのピクセルは一切変わりません。
- 色の変換には `photocraft_cms::transform::cached(src, dst, opts)` を使ってください。変換はプロセス全体で
  キャッシュされ、整数バッファには事前計算テーブルまたはデバイスリンクが使われます。

## メニューのパリティ

`cargo xtask parity` は Photoshop のメニューツリー（`crates/ui-egui/src/menu_catalog.rs`）と
稼働中のコマンドレジストリ（`menus::is_live`）を比較し、[`docs/parity.md`](parity.md) を書き換えます。テスト
`parity::tests::parity_does_not_regress` は、稼働中の項目数が `parity::FLOOR` を下回ると失敗します。

## テスト戦略

- **ユニットテストとプロパティテスト**をすべてのクレートに用意します。proptest はタイルの COW、領域、コーデックに使っています。
- **フォーマット系クレート:**
  - 合成ジェネレーター（`psd::testgen`）
  - バイト単位で一致するラウンドトリップ
  - 不正入力の網羅（あらゆるオフセットで切り詰める）
  - ファズターゲット（`crates/*/fuzz`）
- **実ファイルのコーパス**は `corpus/`（gitignore 対象）にあります。`corpus/psd` には MIT ライセンスのテスト用 PSD が入っており、出典は `corpus/psd/SOURCES.md` に一覧があります。`cargo xtask corpus --download` で PngSuite を取得します。コーパスが存在しない場合、テストは黙ってスキップされます。
- **合成オラクル:** PSD に埋め込まれた統合画像と、自前のコンポジターの出力を比較します。合格率はロードマップで追跡しています。
- **UI:** ウィジェットと状態のユニットテストに加え、制御チャンネル経由のスクリーンショットチェックを行います。

## パフォーマンスに関するメモ

- キャンバスは独自の WGSL シェーダー（`ui-egui/src/gpu_canvas.rs`）で表示します。ミップマップ/ニアレストサンプリング、プロシージャルなチェッカーボード、ピクセルグリッド、タイル分割を備えます。ブラシストロークは変更のあった矩形だけをアップロードします。
- **キャンバスは GPU 上で合成します**（`photocraft-gpu`、`gpu_canvas.rs` から駆動）。レイヤー効果も含みます。プランナーが表現できないものは `Unsupported` を返し、キャンバスは CPU コンポジター（`photocraft-compose`。エクスポートやテストのリファレンスでもある）にフォールバックします。対象はマルチチャンネルドキュメントと、テクスチャ上限を超えるドキュメントや効果領域です。GPU が自前で導出できない要素は CPU で一度だけラスタライズしてキャッシュします（ベクトルマスクには `compose::masks`、クリップされたレイヤーを持つ線付きシェイプには `compose::shape_split`、効果の距離場）。対話的パスの計測: `cargo run --release -p photocraft-ui-egui --example interactive_bench`。効果: `--example fx_bench`（GPU と CPU の比較は `--compare files…`）。大きなドキュメント（オープン、リフレッシュ、サムネイル、フィルター、ストローク、保存。1 回の実行で 1 操作なので `/usr/bin/time -l` でそのピークメモリがわかる）: `--example large_image_bench -- --size 14000x14000 --op psd`。アプリはアダプター自身のテクスチャ上限を要求します（egui のデフォルトは 8192 px。`gpu_canvas::use_adapter_limits` を参照）。それを超える場合は CPU フォールバックが帯状に合成・アップロードし（`compose::render_bands`）、エクスポート、サムネイル、統合も帯単位でストリーミングするため、フルサイズの浮動小数点合成画像を保持することはありません。描画の忠実度: `cargo run --release -p photocraft-io --example oracle_diff -- corpus/psd`（PSD オラクル表全体を数秒で出力）。`ui.inspect` → `perf.timings.gpuFallback` がフォールバックの理由を示します（GPU パスでは `null`）。
- **GPU 上のレイヤー効果**（`gpu/src/fx.rs`、カーネルは `gpu/src/compose.wgsl`）。有効な各効果は、レイヤーの効果領域に対する*マッププログラム*（シフト、膨張、ガウスぼかし、グローのランプ、ベベルの高さとシェーディング、輪郭、境界線の帯）になり、`compose::effects` を 1 ステップずつ再現します。チャンク単位の合成はそのマップを通してその領域内にクリップして描画し、結果を背景にその場でコピーし戻すため、小さなテキストレイヤーのコストはそのピクセル分だけです。レイヤーのシェイプ（`compose::layer_shape`）とその距離場（`compose::effects::distance_field`: 逐次的な変換で、そのタイブレークは並列 GPU パスではビット単位で再現できない）は、compose が CPU 上で並列の帯に分けて計算します。すべてレイヤーの状態ごとにキャッシュされます。無関係な編集や効果の色・不透明度の変更では何も再構築しません。ブラシのダブは、触れた 256² タイルを効果の到達範囲分広げた領域だけを再計算します。1 つの効果のジオメトリを変えた場合はその効果だけを再構築します。キャッシュ予算は `gpu::FX_BUDGET`（1.5 GB、最も長く描画されていないレイヤーから追い出し）。`PHOTOCRAFT_FX_TRACE=1` で各再構築の CPU 時間を出力します。
- キャンバスはストロークの変更矩形を周囲のレイヤーの効果到達範囲（`canvas::effect_reach`）だけ広げるため、ダブの外側の効果も更新されます（両パスとも）。
- **数値**（7360 × 4912、テキストレイヤー 8 枚 + ドロップシャドウ・境界線・ベベル付きのペイントレイヤー 1 枚、その上に色相・彩度。M4 Pro。`cargo run --release -p photocraft-ui-egui --example fx_bench`）、CPU フォールバック → GPU: 効果マップがウォームな状態での全体リフレッシュ 5.7 s → 47 ms、効果の上にある色相・彩度の調整 4.7 s → 31 ms、通常レイヤーへのブラシダブ 32 → 1.7 ms、効果レイヤーへのブラシダブ（ダブ周辺のマップを再構築）659 → 3.7 ms、初回リフレッシュ（全マップを構築）6.4 s → 0.39 s。並列ビルドで CPU が約 14 倍のオーバーサブスクライブ状態（7 回の最小値）では 8.1 s → 0.33 s、9.9 s → 0.28 s、28 → 2.2 ms、1.7 s → 89 ms、テキストレイヤーを 7 px 移動 336 → 13 ms。`fx_bench --compare corpus/psd/…/*.psd` は実ファイルでの GPU と CPU の差を報告します（効果を含むコーパスファイル 31 個中 30 個が GPU で描画され、最大誤差は 0.12/255）。
- CPU パスでは `compose::effect_maps` がシャドウ、グロー、ベベル、サテンのマップをレイヤーの状態ごとにキャッシュします（LRU、予算 768 MB）。
- 大きなドキュメントでの調整のライブプレビューには、ダウンサンプリングしたプロキシ（`ui-egui/src/proxy.rs`）を使います。
- `ui.inspect` は `perf` の計測値（フレームあたりの UI ms、合成 ms、アップロード ms）を返します。
- フレームごとにサーフェス全体を走査してはいけません。ドキュメントのリビジョンごとにキャッシュしてください（`PhotocraftApp::cached_bounds`）。36 MP のレイヤーでキャッシュなしの `content_bounds()` を呼んでいたときは、1 フレームあたり 77 ms かかっていました。

## Web ビルド

`apps/photocraft-web` は eframe の Web ランナーを通して、同じ `PhotocraftApp` をブラウザ上で実行します。レンダラーは wgpu で、ブラウザが対応していれば WebGPU、そうでなければ WebGL2 を使います。Rust のみで書かれており、JavaScript は wasm-bindgen が生成するグルーコードだけです。

```sh
brew install trunk                 # or: cargo install trunk --locked
cd apps/photocraft-web
trunk build --release              # writes ../../dist/web (index.html, .js glue, .wasm)
trunk serve --release              # dev server on http://127.0.0.1:8765
```

`dist/web` はどんな静的ファイルサーバーでも配信できます。たとえばそのディレクトリ内で `python3 -m http.server 8765` を実行します。Trunk は対応する `wasm-bindgen` と `wasm-opt` を自動でダウンロードします。リリース版の `.wasm` は約 12.7 MB（gzip 圧縮で 5.0 MB）です。圧縮して配信してください。

URL フラグ: `?webgl` は WebGL2 バックエンドを、`?cpu` は CPU キャンバスパスを強制します。

Web シェル（`apps/photocraft-web/src/web.rs`）とデスクトップの違い:

- **開く**は `rfd::AsyncFileDialog` を使います。バイト列は非同期に `Services::inbox` に届き、アプリが毎フレームそれを取り出します。
- **保存 / 別名で保存 / 書き出し**は、エンコードしたバイト列のブラウザダウンロードを発生させます。シェルは Blob、オブジェクト URL、一時的な `<a download>` を使ってこれを行い、いずれも Rust から生成します。保存ダイアログはないため、提案されたファイル名がそのままダウンロード名になります。
- **ドラッグ＆ドロップ:** `WebShell` はアプリより先にフレームの `dropped_files` を受け取ります。各ファイルを `DroppedFile::bytes_async` で読み込み、バイト列を inbox に入れます。
- **制御サーバーはありません:** ブラウザは TCP で待ち受けできません。Web ビルドを自動化するには、`--remote-debugging-port` を付けたヘッドレス Chrome を操作します。開くは `Page.setInterceptFileChooserDialog` と `DOM.setFileInputFiles`、ドロップは `files` を指定した `Input.dispatchDragEvent`、ダウンロードの取得は `Browser.setDownloadBehavior` で対応できます。
- macOS 上のヘッドレス Chrome（`--headless=new --enable-unsafe-webgpu`）では実際の WebGPU アダプターが得られます。


## オフスクリーン UI スナップショット（ウィンドウなし）

実際の wgpu キャンバスを使って UI 全体をヘッドレスで描画します。デザインレビューや、アプリの
ウィンドウが隠れてしまう場合に使います（macOS は隠れたウィンドウを描画しないため、ライブの `ui.screenshot` は
ウィンドウを前面に出してフォーカスを奪う必要があります）。

```sh
cargo run --release -p photocraft-ui-egui --example snapshot -- \
    --out ui.png --size 1440x900 --scale 2 --open photo.jpg \
    --script '[["ui.set", {"tool": "type"}], ["ui.menu.invoke", {"id": "image.canvasSize"}]]'
```

`--script` は制御プロトコル呼び出し（`[method, params]`）のリストで、順番に適用されます。
入力系の呼び出し（`ui.key`、`ui.type`、`ui.click`）は、アプリがイベントを処理し終えてから応答するようになったため、
続く `ui.inspect` でその効果を観測できます。


## 描画の忠実度（PSD オラクル）

`cargo test --release -p photocraft-io --test corpus -- --nocapture` は、コーパス内のすべての PSD について
自前の合成結果を Photoshop 自身の統合画像と比較します（PASS ≤ 2/255）。1 つのファイルを詳しく調べるには:

```sh
cargo run --release -p photocraft-io --example oracle_diff -- corpus/psd/<file>.psd 0 png /tmp/diff.png
```

これで自前の結果 | Photoshop | 差分ヒートマップを横に並べて書き出します。`col`、`row`、`worst [n]`、`grid x0 y0 x1 y1 [ch]`、
`layerpx x y`、`DUMP_FX=1` で、サンプル、最も差の大きいピクセル、値のグリッド、レイヤーごとのピクセル、効果の生の
ディスクリプターを出力します。これまでにわかったこと: 塗りつぶしレイヤーのグラデーションはレイヤーマスクの範囲を枠とする。
Photoshop のグラデーションの滑らかさは Catmull-Rom 補間によるブレンドで、「知覚的」補間は Oklab である
（インポート時に密なストップに焼き込む。`crates/io/src/gradient_bake.rs`）。シェイプレイヤーのベクトル
境界線はクリップされたレイヤーより上に描かれる。リンクされた効果パターンはレイヤーの `fxrp`
基準点からタイル状に並ぶ。境界線の距離は 5 × 5 のチャンファー距離（1、√2、√5）に従い、サブピクセルの
エッジオフセットを起点とする。内側の効果はレイヤーのアルファを保持する。外側の境界線はそれぞれのモードで背景に
ブレンドされ、上の境界線が下の境界線を覆う。
