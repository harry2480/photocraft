# PhotoCraft のリリース

`release` ブランチへの push のたびに `.github/workflows/release.yml` が実行されます。このワークフローは
macOS、Windows、Linux、Web 向けの署名済みインストーラーをビルドし、`PhotoCraft v<version>` という名前の **ドラフト**
GitHub Release を作成または更新します。ドラフトはメンテナーが公開するまで誰にも見えません。

これは共通の [リリースプレイブック](リリース手順書.md) の PhotoCraft における実装です。ユーザー向けの名前は **PhotoCraft** と表記します。ファイル、バイナリ、
ID は小文字のままにします（`photocraft-<version>-<platform>-<arch>.<ext>`、`ai.storyteller.photocraft`）。

## リリースの作成手順

1. `main` で**バージョンを上げます**。バージョンが定義されている場所は、ルートの `Cargo.toml` の
   `[workspace.package] version` だけです。

   ```sh
   cargo xtask version                 # prints the current version, e.g. 0.1.0
   cargo xtask version set 0.2.0       # or 0.2.0-rc.1; updates Cargo.toml and Cargo.lock
   ```

   変更（`Cargo.toml` + `Cargo.lock`）は通常のレビューフローでコミットします。
2. **`main` を `release` にマージ**（またはファストフォワード）して push します。ワークフローは自動で開始します。
3. **ドラフトを待ちます。** 30〜45 分ほど（時間がかかるのは公証）で、
   Releases ページに `PhotoCraft v0.2.0` のドラフトが作られます。push したコミットに `v0.2.0` のタグが付き、
   すべての成果物と `SHA256SUMS.txt` が含まれます。リリースノートはマージされた PR から生成されます。
4. **確認します。** インストーラーを 1〜2 個ダウンロードし、ジョブのサマリーを確認してください。そこに
   `::warning::` があれば、署名用シークレットが欠けていて、その成果物は署名されていません。
5. GitHub の UI でドラフトを**公開**します。公開すると `v0.2.0` タグが作成されます。プレリリースの
   サフィックス（`-rc.1`）付きのバージョンはプレリリースとしてマークされます。

公開前に `release` へ再度 push すると、同じドラフトが再ビルドされ、アセットが置き換えられます。
ドラフトの公開後は、ワークフローはそのバージョンを二度と変更しないので、先にバージョンを上げてください。

**テスト実行:** *Actions → Release → Run workflow* で、パイプライン全体を手動で実行できます。任意の
`version` 入力（`0.2.0-rc.1` など）は、その実行に限り `Cargo.toml` の値を上書きします。ジョブはビルド前に
`cargo xtask version set` でこれを適用するので、バイナリもそのバージョンを報告します。この実行でも
`release` environment が必要で、それを使えるのは `release` ブランチだけなので、ダイアログでそのブランチを
選んでください。

## ビルドされるもの

| プラットフォーム | 成果物 | ビルド環境 |
|---|---|---|
| macOS 11+（ユニバーサル: Apple シリコン + Intel） | `photocraft-<v>-macos-universal.dmg`、`photocraft-cli-<v>-macos-universal.zip` | `macos-15` |
| Windows 10+ x64 | `photocraft-<v>-windows-x64.msi`、`photocraft-<v>-windows-x64-portable.zip` | `windows-latest` |
| Windows 10+ x86（32 ビット） | `photocraft-<v>-windows-x86.msi`、`photocraft-<v>-windows-x86-portable.zip` | `windows-latest` |
| Linux x86_64 | `photocraft-<v>-linux-x86_64.{AppImage,deb,rpm,tar.gz,flatpak}` | `ubuntu-22.04`（Flatpak: `ubuntu-24.04`） |
| Linux aarch64 | `photocraft-<v>-linux-aarch64.{AppImage,deb,rpm,tar.gz,flatpak}` | `ubuntu-22.04-arm`（Flatpak: `ubuntu-24.04-arm`） |
| Web | `photocraft-web-<v>.zip`（静的サイト。[`packaging/web/README.md`](../packaging/web/README.md) を参照） | `ubuntu-latest` |

すべてのバイナリは、バージョン、コミット、ビルド日時を報告します: `photocraft --version`、
`photocraft-cli --version`、*ヘルプ › PhotoCraft について*。CI が `PHOTOCRAFT_BUILD_SHA` と
`PHOTOCRAFT_BUILD_DATE` を設定し、`crates/engine/src/build_info.rs` がコンパイル時にそれを読み込みます。単なる
`cargo build` ではこれらが設定されず、`0.2.0 (dev build)` と報告されます。

### macOS

`packaging/macos/package.sh` は `aarch64-apple-darwin` と `x86_64-apple-darwin` を
`MACOSX_DEPLOYMENT_TARGET=11.0` でビルドし、`lipo` で結合して `PhotoCraft.app` を組み立てます。

- `Info.plist` は `Info.plist.in` から生成されます。バンドル ID は `ai.storyteller.photocraft` です。
  plist では `LSMinimumSystemVersion` 11.0、`NSHighResolutionCapable`、ドキュメントタイプを設定します。
  ドキュメントタイプは `.pcraft`（Owner）に加え、PSD/PSB と PhotoCraft が読み込める画像フォーマット（Alternate。プレビュー.app の
  デフォルトを奪わないため）です。アイコンは `assets/app-icon/photocraft.icns` です。
- **署名**は、Hardened Runtime と安全なタイムスタンプを使って内側から外側へ行います。まず実行ファイルに
  署名し、次にバンドルに署名します。最終署名に `--deep` は付けません。
  エンタイトルメント（`entitlements.plist`）は意図的に空にしています。
- **公証:** アプリを zip にして `xcrun notarytool submit --wait` で送信し、その後
  チケットをアプリにステープルします。アプリは DMG（`hdiutil`、ドラッグ先の `Applications` リンク付き）に
  収められます。DMG にも署名・公証・ステープルを行います。スクリプトは
  `codesign --verify --strict`、`stapler validate`、`spctl -a -vvv` で結果を検証します。
- **CLI:** ユニバーサル版の `photocraft-cli` は Hardened Runtime で署名し、zip にして
  公証します。単体のバイナリはステープルされたチケットを保持できないため、Gatekeeper がオンラインで照会します。

証明書のないローカル環境では、スクリプトはアドホック署名（`codesign -s -`）を行い、公証をスキップします。
自分の Mac でバンドルと DMG を確認するにはこれで十分です。

```sh
packaging/macos/package.sh                    # universal; needs both rustup targets
packaging/macos/package.sh --arch aarch64     # quicker, host-only
open dist/release/photocraft-*-macos-*.dmg
```

### Windows

`packaging/windows/package.ps1 -Arch x64|x86` は `-C target-feature=+crt-static` を付けてビルドします。
C ランタイムを静的リンクするため、MSI もポータブル zip も Visual C++
再頒布可能パッケージを必要としません。これはスタンドアロンのインストーラーにとって重要で、増えるサイズは約 100 KB だけです。このフラグは
`CARGO_TARGET_<TRIPLE>_RUSTFLAGS` に指定するので、ホスト側のビルドスクリプトには影響しません。

- `apps/photocraft/build.rs` は `winresource` クレートを使って、アイコン（`assets/app-icon/photocraft.ico`）と
  VERSIONINFO を埋め込みます。これは Windows をターゲットにした場合だけ行われます。それ以外では
  何もせず、Web ビルドはこのクレートに触れません。
- リリースビルドは GUI サブシステムを使うため、スタートメニューから起動してもコンソールウィンドウは開きません。
- `photocraft.wxs`（WiX v5）は、Program Files へのマシン単位インストールで、アドバタイズ型の
  スタートメニューショートカットを作成します。PhotoCraft は `.pcraft` の既定のアプリになり、PSD/PSB と画像ファイルの
  「プログラムから開く」に表示されます。App Paths も登録します（Win+R で `photocraft`）。
  MSI のバージョンは数値の `X.Y.Z` です。MSI にはプレリリースのフィールドがないためです。同一バージョンへの
  アップグレードを許可しているので、リリース候補同士が互いを置き換えられます。
- **署名:** `packaging/windows/sign.ps1` は、SHA-256 と RFC 3161 タイムスタンプを使い、`signtool` で
  両方の `.exe` ファイルに署名した後、`.msi` に署名します。存在する方の署名素材を使います。
  1. `.pfx` ファイル（`WINDOWS_CERTIFICATE`、`WINDOWS_CERTIFICATE_PASSWORD`）。タイムスタンプは
     DigiCert。または
  2. Azure Trusted Signing（`AZURE_*`）。スクリプトが
     `Microsoft.Trusted.Signing.Client` の dlib をダウンロードし、Microsoft のサーバーでタイムスタンプを付けます。

  Windows の署名構成が変わったときに修正するのは、このスクリプトだけです。

Windows 上でローカルに行う場合: `dotnet tool install -g wix --version 5.0.2` を実行してから、
`pwsh packaging/windows/package.ps1 -Arch x64` を実行します。

### Linux

`packaging/linux/package.sh` は FHS ツリーを 1 つ用意し、そこからすべてのフォーマットを作成します。ツリーには
両方のバイナリ、`ai.storyteller.photocraft.desktop`、16 px から 512 px までの hicolor アイコンと
スケーラブル SVG、AppStream メタ情報、`.pcraft`・`.psb`・`.qoi` 用の shared-mime-info ファイルが
含まれます。

これらのフォーマットを選んだ理由:

- **AppImage** はインストール不要でどのディストリビューションでも動きます。
  ダウンロードしてすぐ使える選択肢であり、パッケージが対応していないディストリビューションのフォールバックです。
  メンテナンスされている `AppImage/appimagetool` でビルドしており、その静的ランタイムは libfuse2 を必要としません。
- **.deb** は Debian、Ubuntu、Mint、Pop!_OS、elementary を対象とします。**.rpm** は Fedora、RHEL
  とそのクローン、openSUSE を対象とします。どちらもメニュー、MIME、アイコンキャッシュと統合され（
  `postinst.sh` フック）、クリーンにアンインストールできます。どちらも
  [nfpm](https://nfpm.goreleaser.com/) でビルドします。メンテナンスされた依存関係のない 1 つのツールと 1 つの設定ファイル
  （`nfpm.yaml`）で済みます。クレートに cargo-deb や cargo-generate-rpm のメタデータを持たせる必要がなく、
  Ubuntu 上で両フォーマットをビルドできます。
- **.tar.gz** は `/opt` や `~/.local` を自分で管理する人向けです。
- **Flatpak バンドル**（`.flatpak`）は Flatpak にインストールできる単一ファイルで、サンドボックス化されており、
  新しいバンドルをインストールすれば更新できます。AppImage より Flatpak を好む人向けです。
  `packaging/linux/flatpak-bundle.sh` は、ジョブの `.tar.gz` を
  `packaging/linux/flatpak/ai.storyteller.photocraft.bundle.yml` を使って freedesktop 26.08
  ランタイム上で再パッケージします。Rust のビルドは行わず、`flatpak-builder` 内でネットワークも必要としないため、バンドルには
  他のフォーマットと同じバイナリが入ります。アーキテクチャごとの独立した `flatpak` ジョブ
  （flatpak-builder 1.4 のため `ubuntu-24.04` と `ubuntu-24.04-arm`）が Linux ジョブの
  成果物をダウンロードし、スクリプトを実行し、バンドルをインストールし、スモークテストとしてサンドボックス内で
  `photocraft-cli --version` を実行します。バンドルはランタイムのリポジトリとして Flathub を指定しているので、ユーザーは
  次のようにインストールします。

  ```sh
  flatpak install --user photocraft-<v>-linux-x86_64.flatpak   # pulls org.freedesktop.Platform//26.08 from Flathub if missing
  flatpak run ai.storyteller.photocraft
  ```

  サンドボックスの権限（理由はマニフェストに記載）: X11 フォールバック付きの Wayland、IPC（X11
  共有メモリ）、GPU 用の `dri`、ピクチャとドキュメントへの読み書きアクセス。それ以外の
  ファイルはすべてファイルチューザーとドキュメントのポータルを経由します。ネットワークはないため、
  ユーザーが `flatpak override --user --share=network ai.storyteller.photocraft` を実行するまで、
  `--control` サーバーにはサンドボックス内からしかアクセスできません。ホストのフォントは
  `/run/host/fonts` と `/run/host/user-fonts` から読み込みます。ローカルで行う場合（Linux 上で、`flatpak` と
  `flatpak-builder` があること）: `packaging/linux/package.sh --formats tar && packaging/linux/flatpak-bundle.sh`。
- **Flathub**: `packaging/linux/flatpak/ai.storyteller.photocraft.yml` はソースからビルドするもので、
  Flathub への申請に使える状態です（バンドル用マニフェストと同じランタイムと `finish-args` を維持しており、
  packaging-lint がそれを確認します）。CI ではビルドしません。実際のビルドにはベンダリングしたクレートの
  ソース（`flatpak-cargo-generator.py` で生成する `cargo-sources.json`）が必要で、アーキテクチャごとに
  20 分以上かかります。マニフェストのヘッダーにあるコマンドで手動ビルドしてください。

Linux のバイナリはすべて Ubuntu 22.04 でビルドされ、**glibc ≥ 2.35** が必要です: Ubuntu 22.04+、
Debian 12+、Fedora 36+、RHEL 10、openSUSE Tumbleweed。リンクするのは glibc と libgcc_s だけです。X11、
Wayland、xkbcommon、Vulkan、EGL は実行時にシステムから読み込みます。GPU ドライバーもシステムから
提供される必要があります。そのため、パッケージはこれらを依存関係として宣言し、
AppImage には同梱していません。

Linux 上でローカルに行う場合: [nfpm](https://nfpm.goreleaser.com/install/) をインストールしてから、
`packaging/linux/package.sh`（または `--formats "deb tar"`）を実行します。

### Web

`packaging/web/package.sh` は `trunk build --release` を実行し（`apps/photocraft-web/Trunk.toml` を参照）、
`dist/web` をサンプルの `_headers` と `.htaccess` ファイル、ホスティングガイドとともに zip にします。
サイトは相対 URL だけを使うので、どのパス配下でも iframe 内でも動作します。
[`packaging/web/README.md`](../packaging/web/README.md) では、MIME タイプ、圧縮、
キャッシュ、iframe のスニペット、`?webgl` / `?cpu` フラグを説明しています。

## シークレット

すべてのシークレットはリポジトリの **`release` environment**（*Settings → Environments →
release*）に置きます。デプロイ可能なブランチは `release` に制限してください。`release.yml` のすべてのジョブは
`environment: release` を宣言しているため、シークレットを読めるのはそのブランチへの push か、そのブランチでの手動実行だけです。
各シークレットは任意です。欠けている場合、そのプラットフォームの成果物は署名されず、
実行結果に `::warning::` が表示されます。

| シークレット | 用途 |
|---|---|
| `APPLE_CERTIFICATE` | "Developer ID Application: Learning Machines LLC (DJ6XS33FX8)" を含む base64 の `.p12` |
| `APPLE_CERTIFICATE_PASSWORD` | その `.p12` のパスワード |
| `KEYCHAIN_PASSWORD` | CI の一時キーチェーンのパスワード（未設定ならランダム） |
| `APPLE_ID` | `notarytool` が使う Apple ID |
| `APPLE_PASSWORD` | その Apple ID の App 用パスワード |
| `APPLE_TEAM_ID` | `DJ6XS33FX8` |
| `WINDOWS_CERTIFICATE` | base64 の `.pfx` コード署名証明書 |
| `WINDOWS_CERTIFICATE_PASSWORD` | その `.pfx` のパスワード |
| `AZURE_TENANT_ID`、`AZURE_CLIENT_ID`、`AZURE_CLIENT_SECRET` | Azure Trusted Signing 用のサービスプリンシパル（`.pfx` の代替） |
| `AZURE_SIGNING_ENDPOINT` | 例: `https://eus.codesigning.azure.net` |
| `AZURE_SIGNING_ACCOUNT`、`AZURE_CERT_PROFILE` | Trusted Signing のアカウント名と証明書プロファイル名 |

リリースの作成には `GITHUB_TOKEN` を使います。`contents: write` を持つのは最後のジョブだけです。

macOS では、`packaging/macos/import-cert.sh` が `.p12` をデコードして一時キーチェーンに入れます
（`security create-keychain`、次に `security import`、次に codesign がプロンプトなしで鍵を使えるよう
`set-key-partition-list`）。そして ID の SHA-1 を `MACOS_SIGN_IDENTITY` としてエクスポートします。
キーチェーンはジョブの最後に削除されます。

## アイコン

`assets/app-icon/photocraft.svg` が正式なアイコンです。オーナーが ArtCraft で描いた九尾の狐の絵を
ベクター化したものです（MIT OR Apache-2.0。同じ場所の `LICENSE.txt` を参照。パレットと
ジオメトリは `README.md` に記載）。`packaging/icons.sh` はこれをもとに、1024 px の PNG、`.icns`、`.ico`（
`cargo xtask ico` でパック）、hicolor の PNG を再生成します。`resvg` と、macOS では `iconutil` が必要です。
出力はコミット済みなので、パッケージングでこれらのツールが必要になることはありません。

## チェック

`.github/workflows/packaging-lint.yml` は、`packaging/`、ワークフロー、アイコンのいずれかが
変更されると数秒で実行されます。actionlint、shellcheck、PowerShell のパース、xmllint、
`desktop-file-validate`、`appstreamcli validate`、そして 2 つの Flatpak
マニフェストのランタイムと権限が一致していることを確認する YAML チェックを実行します。
