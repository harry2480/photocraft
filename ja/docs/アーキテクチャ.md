# Photocraft アーキテクチャ

ステータス：ドラフト v1（2026-09-30）。この計画は最終的な UI ツールキットを前提としない。候補については [`rust-framework-options.md`](rust-framework-options.md) で検討している。

この計画では次の事項を定める。
- Cargo ワークスペース
- エンジンを UI から独立させておくためのルール
- UI が実装しなければならないインターフェース
- PSD、合成、ヒストリー、自動化の各部分がどう組み合わさるか

---

## 1. 目標と原則

**目標**
- ネイティブでポータブル（macOS / Windows / Linux）な、完全オープンソースのレイヤー型画像エディタ。時間をかけて Photoshop の機能範囲におおむね匹敵させる。
- コアに手を入れずに **UI を差し替えられる**こと。現在は egui、将来は Slint、Qt などになるかもしれない。
- **コアは `wasm32` にコンパイルできる**こと。これによりブラウザ版デモの可能性を残す。
- PSD の読み書きは **単独で公開できる独自のクレート** に置く。

**原則**

1. **エンジンファースト、ヘッドレスファースト。** すべての機能は GUI なしで、つまりテスト、CLI、MCP から到達できる。GUI はエンジンのクライアントの一つにすぎない。
2. **すべてはコマンドである。** ユーザーに見える各アクションは、型付きでシリアライズ可能なパラメータを持つ安定した `CommandId`（`filter.blur.gaussian` など）を持つ。メニュー、コマンドパレット、ショートカット、記録されたアクション／マクロ、CLI、MCP、プラグインはすべて同じコマンドをディスパッチする。
3. **UI はデータで記述し、ツールキットが描画する。** ツールは *オーバーレイプリミティブ*（線、ハンドル、選択範囲の点線パス）をデータとして生成する。フィルターや色調補正のダイアログは *パラメータスキーマ* から生成される。新しいツールキットはそれぞれに対してレンダラーを一つ実装すればよく、約 150 個の個別ダイアログを作る必要はない。
4. **一つのアルゴリズムに一つのパラメータ構造体。** すべてのアルゴリズムは CPU リファレンス実装（Rust + rayon、決定的）を持つ。一部は GPU 実装（WGSL）も持つ。両者は同じ `#[repr(C)]` `bytemuck::Pod` パラメータ構造体を読む。複数の言語で手作業により同期させたアルゴリズムのコピーを保持することはしない。
5. **イミュータブルなスナップショット、コピーオンライトのタイル。** ピクセルデータは `Arc` で共有される 256² のタイルに格納される。ドキュメントのスナップショット取得は O(レイヤー数) であり、これによりアンドゥ、バックグラウンドジョブ、自動保存、UI からの読み取りが低コストかつロックフリーになる。
6. **決定性。** 同じ入力は、CPU と GPU の間（許容誤差内）、スレッド数の違い、プレビューと書き出しの間で同じ出力を返す。ノイズはドキュメント座標からハッシュで生成する。
7. **デフォルトはピュア Rust。** C/C++ の依存は Cargo フィーチャーの背後、かつ I/O 境界のクレート（たとえば HEIF やオプションの LibRaw）でのみ許可する。
8. **クリーンルーム。** 他のエディタについて調べるのは *振る舞い* のみであり、読めるソースとして配布されている場合であっても、**プロプライエタリなソース（Rust、WGSL、C++、JS）をコピーしてはならない**。仕様は公開されたフォーマット文書（Adobe PSD 仕様、ISO/ICC）、学術論文（PatchMatch、Poisson blending、ARAP）、観察した振る舞いから得る。他製品のコードを貼り付けてはならない。

### 1.1 GIMP の落とし穴を避ける

GIMP への批判は歴史的に正しく、その多くは 2026 年の今も当てはまる。

**ビット深度。**
- GIMP の元のコアは 8 ビット／チャンネルのタイルをハードコードしていた。
- 高ビット深度には GEGL というまったく新しいエンジンが必要だった。GEGL は 2000 年頃に始まり、2.6（2008 年）でオプションとして導入され、移植が完了したのはようやく **GIMP 2.10（2018 年）** で、その移植だけで「6 年間の作業の成果」だった。
- GIMP が 16/32 ビットの整数・浮動小数点処理を得たのはそれ以降である。

**非破壊編集。**
- Photoshop は 1994 年頃から調整レイヤーを持っている。
- GIMP が非破壊の *フィルター* を得たのは **3.0（2025 年 3 月）** で、GTK3 への移植のために 2.10 から約 7 年後だった。
- 非破壊の *レイヤータイプ*（リンクレイヤー、ベクターレイヤー）を得たのは **3.2（2026 年 3 月）** である。

**CMYK。**
- GIMP 3.x は内部的には今も「100% RGB のエディタ」である。
- CMYK は書き出し（JPEG/TIFF/PSD）とソフトプルーフとしてのみ存在する。

**PSD。**
- 読み込みは今も情報が欠落する。Photoshop の調整レイヤーやほとんどのレイヤースタイルは忠実に引き継がれず、テキストは打ち直しが必要になることが多い。
- 3.2 ではレガシーなドロップシャドウとシャドウ（内側）を GIMP のフィルターに変換するようになり、PSB 書き出しが追加された。

**根本原因：** 基本的な性質が **データではなく前提としてコアに焼き込まれていた** ことにある。ピクセル深度、カラーモデル、「レイヤーはピクセルバッファである」という考えがすべてハードコードされていた。後からそれらに触れる機能を追加するたびに、その上に構築されたすべてを書き直す必要があった。

出典：[GIMP 2.10 release notes](https://gimp.org/release-notes/gimp-2.10.html)、[GEGL on Wikipedia](https://en.wikipedia.org/wiki/GEGL)、[GIMP 3.2 release notes](https://www.gimp.org/release-notes/gimp-3.2.html)、[LWN on GIMP 3.0 colour](https://lwn.net/Articles/998793/)。

**初日から採用するルール**（今なら安く済み、どれも後からでは書き直しを強いられる）：

| 性質 | ルール | 場所 |
|---|---|---|
| **ビット深度** | すべてのサーフェスは実行時の `PixelFormat { depth: U8\|U16\|F16\|F32, model, alpha }` を持つ。アルゴリズムは `Sample` トレイト上でジェネリックに書かれ深度ごとに単相化されるか、f32 の作業バッファ上で動作してタイル境界で変換する。エンジンのいかなる公開 API にも `u8` のピクセル型は現れない。CI はゴールデンスイートを 8、16、32f で実行する。 | `raster`、`color`、`algo` |
| **カラーモデル** | `ColorMode`（RGB、Gray、CMYK、Lab、Indexed、Bitmap、およびマルチチャンネル／スポット）は最初から `doc` にある。チャンネル数は動的（1〜N にアルファとスポットを加えたもの）。最初に出荷するのは RGB/Gray の *レンダリング* のみだが、ストレージ、PSD ラウンドトリップ、変換パスは 3 チャンネルや 4 チャンネルを決して前提としない。 | `doc`、`raster`、`psd` |
| **カラーマネジメント** | すべてのドキュメントは ICC プロファイルを持つ。コンポジターは作業空間の記述子を受け取る。表示変換は独立した最終段である。ブレンド空間（ガンマかリニアか）はドキュメントごとのオプションである。 | `color`、`compose` |
| **構造として非破壊** | `LayerContent` は v1 から Adjustment、Fill、Text、Shape、Smart を含む enum であり、任意のレイヤーにスマートフィルターをスタックとして持てる。コンポジターは平坦化したバッファのリストではなく *グラフ* を評価する。破壊的な操作は単に「適用して焼き込む」ことである。 | `doc`、`compose` |
| **ファイルフォーマット** | フォーマットは `trait ImageDecoder/Encoder` と、機能フラグ（深度、モード、レイヤー、アルファ、メタデータ、ICC）を持つレジストリを通じて差し込む。フォーマットの追加はクレートのフィーチャー一つで済む。コアの型の変更を必要としてはならない。可逆な PSD ラウンドトリップは未知のブロックを保持する。 | `codecs`、`io`、`psd` |
| **サイズ** | `TileStore` トレイトの背後にあるタイル化された疎なストレージで、PSB 規模のキャンバス（300k × 300k）に対応する 64 ビット座標を持つ。ドキュメントが一回のアロケーションや一枚の GPU テクスチャに収まることは何も前提としない。 | `raster` |
| **UI ツールキット** | コアはツールキットに決して依存しない（§3〜§4）。GIMP は GTK2 から GTK3 への移植に何年も費やしたが、我々の UI クレートはエンジンに触れずに置き換えられる。 | レイヤリングルール 2 |

判定基準は単純である。**64 ビット浮動小数点、新しいカラーモデル、新しいファイルフォーマットの追加は、土台ではなく末端のクレートだけに触れるべきである。** これをフェーズ 2 で確認する。UI に公開する前の早い段階で、（非公開の）CMYK と 32f のコードパスを追加するのである。

## 2. ワークスペース構成

```text
photocraft/
├─ Cargo.toml                  # [workspace], shared deps, lints, profiles
├─ crates/
│  │  ── foundation (no_std-friendly where practical, wasm-safe) ──
│  ├─ geom/                    photocraft-geom      points, rects, affine/perspective, tile coords, bezier (kurbo)
│  ├─ cms/                     photocraft-cms       pure-Rust ICC colour management: profiles, transforms, intents, BPC, soft proof, 3D LUTs
│  ├─ color/                   photocraft-color     pixel formats, color spaces, blend-mode math (scalar reference); conversions via cms
│  ├─ raster/                  photocraft-raster    tiled COW surfaces, masks, mip pyramids, damage regions, pixel iterators
│  │  ── document ──

│  ├─ gpu/                     photocraft-gpu       wgpu backend for the DrawOp plan + GPU kernels (WGSL), residency cache, memory budget

│  ├─ io/                      photocraft-io        import/export orchestration; doc ⇄ PSD mapping; PDF/SVG import (features)
│  │  ── intelligence ──
│  ├─ ml/                      photocraft-ml        model registry + InferenceBackend trait (ort native / burn|candle web); SAM2, matting, depth, sky
│  ├─ plugins/                 photocraft-plugins   sandboxed WebAssembly filter plug-ins (wasmi host, limits, ABI v1, registry)
│  │  ── the façade every frontend talks to ──
│  ├─ tools/                   photocraft-tools     tool state machines (move, marquee, lasso, brush, clone, gradient, crop, transform, pen, text…)
│  ├─ engine/                  photocraft-engine    Session: open docs, command registry + dispatch, jobs, events, view-models, preferences
│  │  ── platform + frontends ──
│  ├─ platform/                photocraft-platform  traits: file dialogs, clipboard, fonts, tablet input, menus, storage; native + web impls
│  ├─ ui-egui/                 photocraft-ui-egui   the (first) GUI shell: panels, dialogs, canvas widget, theme
│  ├─ automation/              photocraft-automation  MCP server (rmcp) + JSON-RPC over the command registry
│  └─ testkit/                 photocraft-testkit   golden images, perceptual diff, fixtures, PSD corpus helpers
├─ apps/
│  ├─ photocraft/              desktop binary (winit + wgpu + ui-egui + platform-native)
│  ├─ photocraft-cli/          headless batch CLI (open → commands → export), also hosts `mcp` subcommand
│  └─ photocraft-web/          wasm32 binary (ui-egui + platform-web), demo
├─ shaders/                    (or inside gpu/) WGSL, with generated struct headers
├─ assets/                     icons, bundled fonts, default brushes/swatches/presets
├─ fuzz/                       cargo-fuzz targets (psd, codecs, format)
├─ xtask/                      build tasks: layer-check, shader-gen, corpus fetch, release
└─ plan/                       this directory
```

**現時点で存在するもの。** この構成は目標とする設計である。これまでに構築済みなのは `geom`、`cms`、`color`、`raster`、`psd`、`codecs`、`doc`、`ops`、`algo`、`paint`、`text`、`vector`、`compose`、`gpu`、`format`、`raw`、`io`、`plugins`、`engine`、`ui-egui`、`automation`、`testkit`、および 3 つのアプリである。まだ分離されていないもの：`viewport` と `tools` は `ui-egui` と `engine` の中にある。`platform` のサービスは各アプリが注入する関数フック（`ui_egui::Services`）である。`adobe-assets` と `ml` は未着手である。

**クレートの粒度：** まずは上記のクレートから始める。いずれかのモジュールが約 1 万行を超えるか、コンパイル時間が問題になったら、`algo` を `-adjust`、`-filters`、`-select`、`-inpaint`、`-warp` に分割する。内部のモジュール境界はすでにその線に沿っているべきである。

**命名：** ディレクトリ名は短くし、パッケージには `photocraft-` を接頭辞として付ける。`photocraft-psd` を crates.io に公開する場合は、中立的で公開可能な名前（`psd-rw` など）を付ける。

## 3. 依存関係のレイヤリング（強制）

```text
 L7  apps/*                         (binaries: wire everything together)
 L6  ui-egui · automation · platform
 L5  engine
 L4  tools · viewport · io · ml · plugins
 L3  compose · gpu · format
 L2  ops · algo · paint · text · vector
 L1  doc
 L0  geom · cms · color · raster           psd, codecs, raw, adobe-assets (standalone, no workspace deps)
```

**ルール**（CI で `cargo xtask layers` が `cargo metadata` を解析してチェックする）：

1. クレートは **下位** レイヤーのクレートにのみ依存できる。列挙した例外を除き、循環依存や横方向の依存は禁止。
2. **L6 より下のものは、いかなる UI ツールキット、winit、`platform` の実装にも依存してはならない。** プラットフォームサービスは `engine`（または `platform` のトレイトのみのコア）で定義されたトレイトを通じてエンジンに届き、起動時に注入される。
3. **`photocraft-psd` はワークスペース内のどのクレートにも依存しない。** doc ⇄ PSD のマッピングは `io` にある。これにより PSD クレートを公開可能に保ち、他のプロジェクトから再利用できるようにする。
4. **wasm ゲート：** L0〜L5 のすべてのクレート（フィーチャーで切り替えるネイティブバックエンドを除く）は `wasm32-unknown-unknown` 向けにビルドできなければならない。CI は `cargo build -p photocraft-engine --target wasm32-unknown-unknown --no-default-features --features web` を実行する。
5. `gpu` は `engine` にとってオプションである。エンジンのフィーチャーは `gpu`（デフォルトで有効）と `cpu-only` であり、ヘッドレス CLI と CI のテストは `cpu-only` ビルドを使う。
6. **C 依存**（libheif、オプションの LibRaw、pdfium）はフィーチャーの背後でのみ、`codecs`、`raw`、`io` の中でのみ使い、Web ターゲットではデフォルトで決して有効にしない。

## 4. UI 差し替えの継ぎ目（最も重要なインターフェース）

フロントエンドがコアから必要とするものはちょうど 5 つである。これらを小さくデータ指向に保つことが、UI を置き換え可能にする。

### 4.1 `Session`：コマンドを入れ、イベントを出す

```rust
// photocraft-engine
pub struct Session { /* docs, registry, job pool, prefs, services */ }

impl Session {
    pub fn new(services: Services) -> Self;                         // platform traits injected
    pub fn dispatch(&self, doc: Option<DocId>, cmd: CommandInvocation) -> Result<JobHandle, CommandError>;
    pub fn registry(&self) -> &CommandRegistry;                     // metadata for menus/palette/shortcuts
    pub fn snapshot(&self, doc: DocId) -> Arc<DocSnapshot>;         // lock-free read (arc-swap)
    pub fn events(&self) -> EventReceiver;                          // DocChanged{damage}, JobProgress, Toast, …
    pub fn view_models(&self, doc: DocId) -> ViewModels;            // layers, history, channels, tool options…
}

pub struct CommandInvocation { pub id: CommandId, pub params: serde_json::Value /* validated vs schema */ }
```

### 4.2 `CommandRegistry`：メニュー、パレット、自動化のカタログ

各コマンドは次のものを登録する。
- `id`（`"filter.blur.gaussian"`）、`label`、`menu_path`（`["Filter","Blur"]`）、`default_shortcut`。
- `params: schemars::Schema` と、オプションの `ui_hints`（スライダーの範囲、単位、対数スケール、グルーピング）。
- `enabled(&DocSnapshot, &ToolState) -> bool` と `checked(...) -> Option<bool>`。
- `preview: PreviewMode`（None / Live / Proxy）。これによりダイアログはキャンバス上のプレビューを汎用的に表示できる。
- `kind`：Instant / Dialog / Interactive（ツールに制御を渡す。例：自由変形）。

**利用者：**
- GUI はこれからメニューバー、⌘K パレット、ショートカットエディタを構築する。
- `automation` はレジストリを MCP ツールとして公開する。
- `photocraft-cli` は `photocraft run --cmd filter.blur.gaussian --param radius=4 in.psd out.png` を公開する。
- アクションの記録は単なる `Vec<CommandInvocation>` である。

### 4.3 ツール：ポインターイベントを入れ、操作とオーバーレイを出す

```rust
// photocraft-tools
pub struct PointerEvent { pub pos_doc: Point, pub pressure: f32, pub tilt: Vector, pub twist: f32,
                          pub time_us: u64, pub buttons: Buttons, pub mods: Modifiers, pub kind: PointerKind /* mouse|pen|eraser|touch */ }

pub trait Tool {
    fn id(&self) -> ToolId;
    fn options_schema(&self) -> Schema;                       // options bar generated from schema
    fn on_pointer(&mut self, ev: &PointerEvent, cx: &mut ToolCx) -> ToolResponse;   // ToolCx gives snapshot + op sink
    fn on_key(&mut self, key: Key, cx: &mut ToolCx) -> ToolResponse;
    fn overlay(&self, view: &ViewTransform) -> Vec<OverlayPrim>;                     // drawn by any UI
    fn cursor(&self) -> CursorSpec;
}

pub enum OverlayPrim { Path{path: BezPath, style: StrokeStyle, space: Space}, MarchingAnts{path: BezPath},
                       Handle{pos: Point, kind: HandleKind}, BrushOutline{center: Point, radius: f32, ..},
                       Text{pos: Point, text: String}, Guide{..}, Grid{..} }
```

高レートでまとめられた（coalesced）ペンのサンプルは `platform` から届き、バッチとしてツールに渡される。そのため UI が 60〜120 Hz で描画していても、ブラシはすべてのサンプルを受け取れる。

### 4.4 ビューポート：ドキュメントからピクセルへ

```rust
// photocraft-viewport
pub struct Viewport { pub camera: Camera /* zoom, pan, rotation, dpr */, /* tile/mip cache */ }
impl Viewport {
    pub fn render_gpu(&mut self, snap: &DocSnapshot, gpu: &GpuContext, target: &wgpu::TextureView, damage: &Region);
    pub fn render_cpu(&mut self, snap: &DocSnapshot, target: &mut RgbaImageMut, damage: &Region); // wasm fallback, tests
    pub fn doc_to_screen(&self) -> Affine;  pub fn screen_to_doc(&self) -> Affine;
}
```

- `wgpu::TextureView` をホストできるツールキット（egui のペイントコールバック、Slint の wgpu テクスチャインポート、Bevy、素の winit サーフェス）であれば、どれも同じ方法でキャンバスを埋め込める。
- wgpu を持たないツールキットは `render_cpu` にフォールバックできる。

### 4.5 ビューモデルとスキーマ

- パネル（レイヤー、ヒストリー、チャンネル、パス、プロパティ、ナビゲーター、ヒストグラム、スウォッチ）は、スナップショットから生成されたプレーンな構造体を読む。たとえば `LayersModel { rows: Vec<LayerRow{ id, name, kind, depth, visible, locked, thumb: ThumbHandle, blend, opacity, has_mask, effects: Vec<..> }> }` である。サムネイルは `ThumbHandle` であり、UI はエンジンのサムネイルキャッシュを通じてそれをテクスチャに解決する。
- ダイアログはコマンドの `params` スキーマから生成される。ツールキットは、いくつかの複雑なコマンド（トーンカーブ、レベル補正、Camera Raw、ゆがみ、レイヤースタイル）に対して *カスタム* のダイアログウィジェットを登録してよい。

**継ぎ目のリトマス試験：** `apps/photocraft-cli` と自動化サーバーは、GUI ができることを *すべて* 実行できなければならない。ただしポインターによるペイントは例外で、これは `PointerEvent` のストリームをツールを通じて再生することで行う。

## 5. ドキュメントモデル（`photocraft-doc`）

```rust
pub struct Document {
    pub id: DocId, pub size: Size, pub resolution_dpi: f32,
    pub mode: ColorMode /* Rgb | Gray | Cmyk | Lab | Bitmap | Indexed */, pub depth: Depth /* U8 | U16 | F32 */,
    pub profile: IccProfileRef,
    pub root: LayerGroup,            // tree
    pub channels: Vec<AlphaChannel>, // saved selections/spot
    pub paths: Vec<NamedPath>, pub guides: Guides, pub slices: .., pub metadata: Metadata /* XMP, EXIF */,
    pub selection: Option<Mask>,     // current selection (a raster mask + optional vector outline)
}

pub struct Layer { pub id: LayerId, pub name: String, pub visible: bool, pub locks: Locks,
                   pub blend: BlendMode, pub opacity: f32, pub fill_opacity: f32, pub clipped: bool,
                   pub mask: Option<RasterMask>, pub vector_mask: Option<VectorMask>,
                   pub effects: Effects, pub blend_if: BlendIf, pub content: LayerContent }

pub enum LayerContent {
    Raster(TiledSurface),
    Group(LayerGroup /* children, pass-through or isolated */),
    Adjustment(Adjustment /* Curves, Levels, HueSat, … as params */),
    Fill(Fill /* solid | gradient | pattern */),
    Text(TextLayer /* runs, paragraph styles, warp; cached raster */),
    Shape(ShapeLayer /* vector paths + fill/stroke */),
    Smart(SmartObject /* embedded or linked source + transform + smart filters */),
}
```

- **ピクセル。** `raster::TiledSurface<F>` は `TileCoord` から `Arc<Tile<F>>` への疎なマップで、タイルは 256×256 である。存在しないタイルは透明か、塗りつぶし値をとる。変更時には `Arc::make_mut` を呼ぶので、コピーオンライトになる。
- **タイルの世代カウンター** は GPU のレジデンシーキャッシュとサムネイルキャッシュに使われる。
- **ミップピラミッド** は縮小表示のために、レイヤーごとに遅延生成される。
- **大きなドキュメント。** タイルストアは `TileStore` トレイトの背後にある。現在はインメモリ、将来はディスクへの退避（「仮想記憶ディスク」）を行い、グローバルなメモリ予算のもとで LRU 追い出しを行う。
- **最初のマイルストーンでは RGB と Gray を 8/16/32f でサポートする。** CMYK と Lab は初日から型としてモデル化されている（PSD ラウンドトリップで失われないように）が、後のフェーズまでは RGB に変換してレンダリングする。

## 6. 操作とヒストリー（`photocraft-ops`）

- **すべての変更は `Op` である。** たとえば `SetLayerProps`、`PaintTiles{layer, tiles_before, tiles_after}`、`AddLayer`、`MoveLayer`、`ApplyFilter` など。
- **コマンドはラベル（「ぼかし（ガウス）」）付きの、op の `Transaction` を生成する。**
- **ヒストリーはトランザクションを保存する。** タイルは `Arc` で共有されているため、「変更前」の状態のコストは実際に変更されたタイルの分だけである。アンドゥは `Arc` を入れ替えることを意味し、ピクセルのコピーは発生しない。
- **ブラシストローク** は 1 ストロークにつき 1 トランザクションに蓄積される。タイルは損傷領域（damage region）とともに逐次公開されるため、ビューポートはリアルタイムに更新される。
- **読み手のためのスナップショット。** op がコミットされるたびに、エンジンは `arc-swap` を通じて新しい `Arc<DocSnapshot>` を公開する。UI、バックグラウンドジョブ（フィルター、AI 推論、書き出し）、自動保存はロックなしでスナップショットを読む。
- **バックグラウンドジョブ** はスナップショット N から計算し、トランザクションとしてコミットする。その間にドキュメントが変更されていればジョブはリベースする。つまり同じレイヤー id がまだ存在すればそれを対象にし直し、存在しなければ競合を報告する。
- **ヒストリー機能：** ヒストリーパネル、古いものから追い出すメモリ上限、名前付きスナップショット。ヒストリーブラシは後で実装し、過去の状態からタイルを読む。

## 7. レンダリング

### 7.1 プランナー（`compose`）

`plan(&DocSnapshot, region) -> Vec<DrawOp>` はレイヤーツリーを線形な命令列に平坦化する。
- `PushGroup{isolated, blend, opacity}` / `PopGroup`
- `BeginClipBase` / `Clipped`
- `DrawTiles{layer, blend, opacity, mask}`
- `Adjust{program}`
- `Effect{kind, params}`
- `Fill{...}`

両方のバックエンドが同じプランを消費する。Photoshop のレイヤーのセマンティクス（通過グループ、クリッピンググループ、塗りと不透明度の違い、ブレンド条件、ノックアウト）をエンコードしているのはここだけである。

### 7.2 バックエンド

- **CPU（`compose`）。** リファレンス実装で、rayon を使ってタイルごとに処理する。書き出し、テスト、CLI、および WebGPU が使えない場合の Web のフォールバックで使われる。
- **GPU（`gpu`）。** 同じプランを実行する wgpu のコンピュートおよびレンダーパイプライン。以下を用いる。
  - `rgba16float`/`rgba32float` のアキュムレーター
  - ブレンドファミリーおよび色調補正ごとに特殊化されたパイプライン（一つの巨大な `switch` ではなく、WGSL の `override` 定数）
  - `(TileId, generation)` をキーとするレジデンシーキャッシュ
  - 世代によって無効化される、グループとエフェクトのキャッシュ済み結果
  - GPU メモリのための単一のグローバルな `Budget`
- **パリティテスト。** すべての描画モード、色調補正、エフェクトについて、CPU と GPU の結果は 8 ビット出力で ≤1/255 の許容誤差内で一致しなければならない。これは CI 上でソフトウェアアダプター（lavapipe または WARP を使う wgpu）で実行する。

### 7.3 カラー

- ブレンドはデフォルトでドキュメント空間で行われ、これは Photoshop 互換である。ドキュメントごとの「リニアライトでのブレンド」オプションも利用できる。
- **表示変換**（`engine/src/display_color.rs`）：キャンバスは常にカラーマネジメントされ、ドキュメントプロファイル → モニタープロファイル（相対的な色域を維持 + 黒点の補正）で変換される。これは（ドキュメントプロファイル、モード、モニター）ごとにキャッシュされる。GPU キャンバスでは、変換に加えて色の校正／色域外警告／32 ビットプレビューを 33³ の 3D LUT に焼き込み、キャンバスシェーダーの最終パスでそれを適用する。CPU キャンバスでは合成結果に対して 8 ビットの `photocraft-cms` 変換を実行する。ドキュメントプロファイルがモニターと一致する場合（sRGB 上の sRGB）は、LUT も変換も使わない。リニアな合成結果（EXR/HDR、読み込み時にリニア sRGB としてタグ付けされたもの）は、8 ビットのキャンバステクスチャに sRGB エンコードで格納される。CMYK ドキュメントは埋め込まれた CMYK プロファイルを通じて読まれる（`photocraft_color::convert::with_cmyk_space`。コンポジターと合成結果の書き出しから入る）。
- **モニタープロファイル：** 編集 › カラー設定 › モニタープロファイル。`auto`（macOS では起動時に `osascript`/AppKit の `NSScreen.colorSpace.ICCProfileData` を通じて FFI なしで読み取ったメインディスプレイのプロファイル、それ以外では sRGB）、組み込みの RGB プロファイル、または `.icc` のパスを指定できる。ウィンドウを別のディスプレイに移動しても、プロファイルは再読み込みされない。
- **HDR/EDR 出力**（拡張範囲のカラースペースを持つ `rgba16float` サーフェス）は後のフェーズの機能である。インターフェースはすでに `f32` ピクセルを扱っている。

### 7.4 オラクル

**PSD ファイルには Photoshop 自身による統合済みの合成画像が含まれている。** PSD のレイヤーに対して我々のコンポジターを実行し、埋め込まれた合成画像との差分をとれば、無料で大規模な適合性テストスイートが得られる。`testkit` はこれを PSD コーパスに対して自動化する。

## 8. `photocraft-psd`：独立した PSD/PSB クレート

**範囲：** PSD（v1）と PSB（v2、64 ビット長）の、フォーマットレベルでの忠実な読み書き。我々のドキュメントモデルへの依存はない。

```text
psd/src/
  header.rs         color mode, depth, size
  color_mode_data.rs
  resources/        image resources (1005 resolution, 1036 thumbnail, 1039 ICC, 1060 XMP, 1058 EXIF, slices, guides, …)
  layers/           layer records, channel image data (raw | RLE/PackBits | ZIP | ZIP+prediction), masks, blending ranges
  tagged/           additional layer info blocks, one module per key:
                    luni lsct lyid lfx2/lrFX (effects) TySh (text) SoLd/PlLd/lnk2 (smart objects) vmsk/vsms/vogk (vector)
                    adjustment keys (curv levl hue2 blnc selc mixr grdm phfl brit thrs post nvrt expA vibA clrL blwh)
                    SoCo GdFl PtFl (fills), Patt, Txt2, …
  descriptor.rs     ActionDescriptor / OSType parser+writer (used by many tagged blocks)
  engine_data.rs    text "EngineData" (PostScript-like) parser+writer
  image_data.rs     merged composite
  write.rs          serializer (+ RLE/ZIP encoders)
```

- **可逆なラウンドトリップ。** 未知またはサポート外のタグ付きブロックは生のバイト列として保持し、変更せずに再出力する。こうすることで、3D やビデオのようにまだモデル化していない機能もファイルに残る。
- **遅延デコード。** パーサーはチャンネルデータにインデックスを付け、要求があったときにのみデコードする。これにより 2 GB の PSB を高速かつメモリ使用量を抑えて開ける。
- **書き込み時の統合済み合成画像は呼び出し側が** 画像バッファとして提供する。`io` が `compose` でそれをレンダリングするので、`psd` はコンポジターを必要としない。
- **マッピングは `io::psd` にある。** `psd::File` を `doc::Document` に変換し、また逆に変換する。忠実度のレベルは次のとおり。
  1. 統合された画像。
  2. ラスターレイヤー、マスク、描画モード／不透明度／塗り、表示状態、名前。
  3. グループ（通過を含む）、クリッピング、ブレンド条件、調整レイヤーと塗りつぶしレイヤー。
  4. レイヤー効果（lfx2）。
  5. テキストレイヤー：`text` でシェーピングし、元の記述子はラウンドトリップのために保持する。
  6. スマートオブジェクト：埋め込みとリンク。
  7. ベクトルマスクとシェイプレイヤー。
- **テスト：**
  - 未変更ファイルのラウンドトリップにおけるバイト安定性。
  - 開く → 保存 → 開くの同一性。
  - 合成画像オラクルとの差分（§7.4）。
  - パーサーに対する `cargo-fuzz`。
  - MIT/BSD ライセンスのテストセット（ag-psd、psd-tools）から作るコーパス。`xtask` で取得し、コミットはしない。
- **既存のクレート：** `psd`（読み取り専用、限定的）と、新しい `ag-psd` の Rust 移植版。スパイク第 1 週でこれらを評価し、どれかに依存するか、フォークするか、自作するかを決める。PSD の中心的な重要性を考えると、安定した API の背後で自作する可能性が高い。

## 9. ネイティブファイルフォーマット（`photocraft-format`）

- **フォーマット：** `.pcraft` ファイルは zip（無圧縮格納モード）またはディレクトリのバンドルである。
  - `manifest.json`：serde によるバージョン付きのドキュメントツリーで、`format_version` とマイグレーションを含む。
  - `tiles/<blake3>.zst`：コンテンツアドレス方式の、zstd で圧縮されたタイル。
  - クイックルックとプレビュー用の `thumb.png` と `composite/` のミップ。
- **保存はインクリメンタルである。** タイルはコンテンツアドレス方式なので、保存時には新しいタイルとマニフェストだけを書き込み、参照されていないタイルをガベージコレクトする。
- **自動保存とクラッシュリカバリー** は同じライターを再利用してリカバリー用ディレクトリに書き込み、バックグラウンドスレッドでスナップショットから読み取る。
- **PSD は交換用フォーマットであり、** `.pcraft` は可逆なネイティブフォーマットである。

## 10. アルゴリズム（`algo`、`paint`、`text`、`vector`、`ml`）

| 領域 | 内容（第一段階） | GPU カーネル？ |
|---|---|---|
| 色調補正 | レベル補正、トーンカーブ、明るさ・コントラスト、露光量、自然な彩度、色相・彩度、カラーバランス、白黒、レンズフィルター、チャンネルミキサー、グラデーションマップ、特定色域の選択、階調の反転／ポスタリゼーション／2 階調化、3D LUT | あり（LUT + 小さなカーネル） |
| フィルター | ぼかし（ガウス／ボックス／移動／放射状／表面／レンズ）、アンシャープマスク／スマートシャープ、ハイパス、ノイズの追加／低減／中間値／ダスト＆スクラッチ、変形系（渦巻き、波形、極座標、球面、置き換え）、表現手法、描画（雲模様、逆光）、ピクセレート | 多数 |
| 選択範囲 | 長方形選択／なげなわのジオメトリ → マスク、自動選択（塗りつぶしの許容値）、色域指定、クイック選択（グラフカット／スーパーピクセル）、ぼかし、拡張／縮小、境界線を調整 | 一部 |
| インペイント／修復 | スポット修復、修復ブラシ（Poisson）、コンテンツに応じた塗りつぶし（PatchMatch + マルチスケール EM） | 後で |
| ワープ | 自由変形（アフィン／遠近法／ワープメッシュ）、ゆがみ、パペットワープ（ARAP）、レンズ補正、リサンプリング（Lanczos/バイキュービック） | あり |
| ペイント（`paint`） | ダブ生成（硬さ、真円率、角度、間隔、散布）、筆圧／傾き／速度によるダイナミクス、スムージング（引っ張られる糸／レイジーマウス）、ウェットエッジ、エアブラシ、消しゴム、コピー元／修復元、ストロークごとの描画モード、`.abr` の読み込み | まず CPU、後で GPU |
| テキスト（`text`） | フォント DB トレイト（ネイティブではシステムフォント、Web ではバンドルフォント）、parley によるレイアウト、ランごとのスタイル、段落オプション、ワープ。ラスターキャッシュにレンダリングする | — |
| ベクター（`vector`） | シェイプ、ベジェパス、ペンツールのジオメトリ、ストローク（破線、整列、線端）、ブール演算 → vello_cpu によるカバレッジ | — |
| ML（`ml`） | `InferenceBackend` トレイト。タスク：`segment_point/box`（SAM2）、`matte_subject`（背景の削除）、`depth`、`sky`。SHA-256 検証とオンデマンドダウンロードを備えたモデルレジストリ | バックエンド依存 |

**すべてのアルゴリズムに共通するルール：**
- **シグネチャ：** 純粋関数 `fn(input: &SurfaceView, params: &P, region: Rect, cancel: &CancelToken) -> Surface`。
- **パラメータ：** `P: Pod + JsonSchema + Serialize + Deserialize`。
- **登録：** algo クレート自身ではなくエンジンがコマンドレジストリに登録する。これにより `algo` は UI にもエンジンにも依存しないままでいられる。
- **タイル：** タイルを意識し、`radius` ピクセル分の入力ハロー（周辺領域）を要求する。
- **テスト：** `testkit` でのゴールデン画像テストと、criterion によるベンチマーク。

## 11. エンジンの実行時モデル

```text
 UI thread ──dispatch()──► Engine thread (owns mutable docs, applies ops, publishes snapshots)
     ▲                         │  spawns
     │ events (damage, progress)│
     │                         ▼
     │                  Job pool (rayon): filters, AI, export, autosave — read snapshots, return transactions
     │
 Render (UI thread or dedicated): Viewport::render_gpu(snapshot) into toolkit texture
```

- **低遅延のためのペン入力経路：** プラットフォームのまとめられたサンプル → ツール（エンジンスレッド上）→ COW タイルへのダブのラスタライズ → 損傷領域の公開 → ビューポートは損傷したタイルだけを再合成する。目標：ストロークが次のフレーム内に表示されること。
- **キャンセル：** すべてのジョブは `CancelToken` を受け取り、UI は進捗を持つ任意のジョブをキャンセルできる。
- **`Session` に注入されるサービス：**
  - `FileSystem`（ネイティブの fs ／ Web の File System Access ／テスト用のインメモリ）
  - `Clipboard`、`FontSource`、`ModelStore`
  - `Clock`、`Notifier`

## 12. 自動化と拡張性

- **`automation`：** `rmcp` で構築した MCP サーバー。次のものを公開する。
  - `session.list`、`doc.open`、`doc.save`、`doc.export`、`doc.inspect`（JSON でのレイヤーツリー）、`doc.render_preview`（PNG）。
  - `command.list` と `command.run(id, params)`。どちらもレジストリから生成される。
  - エージェント CLI 向けの stdio と、オプションで、実行中の GUI に接続できるようにするトークン付きのループバック TCP。
  - `AuthorizedWorkspace`。読み取りと書き込みのディレクトリ権限を独立して保持する。リモートの
    パスは検証済みの相対名である。環境のファイルシステムへのアクセスをまだ必要とするエンジンコマンドは、
    自動化の境界でフェイルクローズする（失敗して拒否される）。
- **アクション：** 記録された `Vec<CommandInvocation>` で、バッチで再生できる（ファイル → 自動処理 → バッチ）。
- **スクリプティング（後で）：** 同じレジストリの上にスクリプト言語を組み込む。選択肢は Rhai、または mlua（C）経由の Lua。Photoshop スクリプトとの親しみやすさを求めるなら、QuickJS による JS も可能である。
- **プラグイン：** サンドボックス化された WebAssembly のフィルタープラグイン（`photocraft-plugins`、L4）は、ピュア Rust のインタープリターである `wasmi` で実行され、フューエル、メモリ、スタック、実時間の制限を持ち、ホストのインポートはない。これらは `plugin.*` コマンドで駆動され、フィルター › プラグイン の下に一覧表示される。ABI は [`plugins.md`](プラグイン.md) にある。Photoshop ネイティブの `.8BF`/CEP/UXP のホスティングは対象外である（unsafe な FFI が必要で、Web 上で動作できないため）。パネルプラグインは後で対応する。

## 13. テストと品質

| レイヤー | 内容 |
|---|---|
| ユニット | クレートごと。アルゴリズムは手計算した小さなフィクスチャと照合する |
| ゴールデン画像 | `testkit::assert_image_eq(actual, "golden/name.png", tol)`。ゴールデンは `xtask bless` で再生成する |
| CPU/GPU パリティ | すべての GPU カーネルを CPU リファレンスと比較。CI ではソフトウェアアダプターを使う |
| PSD | ラウンドトリップ、合成画像オラクル、ファジング |
| エンジン | コマンドレベルのテスト：フィクスチャを開く → コマンドをディスパッチ → スナップショット／レンダリングを検証。アクションの再生 |
| UI | パネルのためのヘッドレスな egui テスト（egui_kittest）。UI が薄いので、テストも薄く保つ |
| パフォーマンス | criterion のベンチマーク + CI での予算チェック（4k² で 20 レイヤーの合成、ブラシダブのスループット、100 MP を開く） |
| 移植性 | CI マトリクス：macOS arm64、Windows x64、Linux x64、wasm32 のビルドチェック |

**v1 のパフォーマンス目標：**
- 120 Hz で、ストロークからピクセルまで 1 フレーム以内。
- 100 MP／30 レイヤーのドキュメントで、ディスプレイのリフレッシュレートでのパンとズーム。
- 100 MP の JPEG を 1.5 秒未満で開く。
- 16 GB のマシンで 20k×20k の 16 ビットドキュメント。

## 16. 未決定事項

1. **UI ツールキット。** 最有力は winit + wgpu 上の egui。代替は Bevy、Slint、Qt（`rust-framework-options.md` を参照）。この計画はそのどれとでも機能する。
2. **ライセンス。** MIT/Apache-2.0 は再利用性が最大である。GPL-3.0 は Krita/GIMP のモデルで、プロプライエタリなフォークから守る。候補となる依存の一部は LGPL（rawler）や GPL または商用（Slint）であり、MIT/Apache を選ぶとそれらのうちどれを使えるかが制約される点に注意。
3. **プロジェクト名。** `photocraft`（リポジトリ名）を想定している。
4. **PSD クレート。** 自作するか、`ag-psd`/`psd` を採用またはフォークするか。第 1 週のスパイクの後に決める。
5. **デフォルトの作業深度とブレンド。** 8 ビット + ガンマ空間でのブレンドは Photoshop に一致する。16 ビット／浮動小数点 + リニアは現代的なデフォルトである。提案としては、デフォルトでは Photoshop に従い、もう一方をドキュメントごとのオプションとする。
6. **Photoshop プラグイン互換性の範囲。** 決定済み：ネイティブの `.8BF` のホスティングは行わない。代わりにサンドボックス化された WebAssembly プラグイン API を提供する（[`plugins.md`](プラグイン.md) を参照）。
